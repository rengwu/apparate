## Tuning evidence and remaining limits

The initial single-threaded 200k baseline (one repetition per prefix) measured name p95 **50.924 ms** and path p95 **267.044 ms**. Its [raw samples](../../evidence/2026-11-18T154000Z-m1/baseline-200k.json) and [input fingerprint](../../evidence/2026-11-18T154000Z-m1/baseline-source-manifest.json) are retained as development evidence, not as the final build result. The full earlier source snapshot was not archived; the final source manifest is the reproducible handoff identity.

The final implementation skips candidates whose best possible tier/kind cannot enter the heap, uses the finite closed-form score for an optimal consecutive prefix, and caches repeated ancestor-chain scores for each query. It does not add parallel scoring. The exhaustive-alignment and bounded-versus-exhaustive tests guard those optimizations.

Final name p95 at 200k is below the guide's 8 ms core diagnostic target; path p95 remains above it. That path result and the immediate post-build footprint are review points. They do not justify an end-to-end app pass or an automatic switch to parallel work. The benchmark is synthetic, does not control other activity on the machine, and has no UI/discovery/action work.

Outside the selected M1 scope, therefore **not tested here**: real app/settings discovery, folder crawling and rebuilds, permission prompts, opening items/URLs, system actions, hotkey, panel rendering, visible latency, idle CPU, launch-at-login and upgrades. These remain later milestone work. Independent review passed with the packaging fix recorded below; no commit has been made.
