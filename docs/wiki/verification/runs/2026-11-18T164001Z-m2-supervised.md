## Scope and prerequisites

Covers native integration for [FEAT-apps](../../features/apps.md), [FEAT-settings-items](../../features/settings-items.md), [FEAT-actions](../../features/actions.md), [FEAT-panel](../../features/panel.md) and [FEAT-access](../../features/access.md). The build has been prepared for macOS 27 arm64. Record its source-manifest and binary hashes from the automated run, then recheck signature/version before starting. A changed build requires a new fingerprint.

The user chooses a quiet time and a temporary APPARATE_HOME that will persist through the two signing checks. Seed its config with an available alternate shortcut (for example Control-Option-Command-F12, keyCode 111, modifiers 6400); never try Command-Space during development. Use the normally launched signed `build/Apparate.app` through LaunchServices, with APPARATE_HOME and `APPARATE_SHOW=setup` explicitly supplied to that launch. **Do not set APPARATE_TEST_MODE**: the automated profiles intentionally replace all effects and cannot validate these cases. Confirm no other Apparate instance is running. Record the launched instance's PID so cleanup addresses only that instance.

A prepared LaunchServices command (execute only during the supervised session, after creating and seeding that directory) is:

```sh
open -n --env "APPARATE_HOME=$apparate_check_home" --env APPARATE_SHOW=setup build/Apparate.app
```

`apparate_check_home` must name the same test-created directory for both launches. `open --env` was checked against the installed tool's usage output, but this native launch command has not been executed by the automated run.

Before running Lock, Sleep or Restart, the user must explicitly choose to perform that command at that time and save work. The recipe does not grant blanket permission for disruptive commands.
